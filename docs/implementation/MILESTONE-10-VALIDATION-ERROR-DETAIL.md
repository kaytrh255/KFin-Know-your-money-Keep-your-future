# Milestone 10 addendum — named contract rules for rejected requests

**Implemented:** 2026-10-12<br>
**Base:** `66494d2c3edc753c6ed1af5cf23a070c208bad13` on `arena/bfaf5019-kfin-know-your-money-keep-your` (`main` at `28ee85f2c0137a97d52133bff471526d8b661926`)<br>
**Frozen SDD baseline:** `a48d2c5683550859c1b4e19e9d06750616adc0a2` (unchanged)<br>
**Scope:** Make a rejected request identifiable — name the field and the rule in the response, log the same value-free summary against the correlation ID, and publish the rules the service actually enforces<br>
**Production readiness:** Not claimed

## Why this addendum exists

A registration from the running preview client answered:

```
HTTP 400
code:            REQUEST_VALIDATION_FAILED
message:         The request does not match the API contract.
correlation id:  4f6c54eb-1a71-4b19-a9c3-be28579bfb99
```

Every part of that was unactionable. The message named no field, so the person
registering could not correct anything; the correlation ID existed in no log, so
nobody could look it up; and for the one field whose rule is unforgiving — the
invitation code — the published contract did not state the rule at all, so a
caller following the documentation could be refused by a rule the documentation
never mentioned.

The correlation ID was searched for in every log the process writes, in the
database, and in the platform artifacts left in the sandbox. **It is not retained
anywhere**, by construction:

- `apps/api/src/app.ts` builds Fastify with `disableRequestLogging: true` and
  `requestIdHeader: false`, so no request is logged and the ID is API-generated;
- the `REQUEST_VALIDATION_FAILED` branch sent a response and logged nothing;
- the service never ran, so no `users`, `security_events`, or `audit_events` row
  was written.

The request itself is therefore unrecoverable, and this note does not pretend
otherwise: **which field the caller broke could not be recovered from that
attempt.** What can be fixed is that no future attempt is unrecoverable.

## What was measured

| Check | Result |
|---|---|
| The reported correlation ID, in every log the API writes | absent |
| `requestIdHeader` / `request.log` for a rejected body | ID generated by the API; request logging disabled; the validation branch emitted nothing |
| Trace of the rejected request in the database | none — no user, invitation, security event, or audit row |
| The client's register payload, field by field, against `registerBodySchema` | matches: `email`, `password`, `invitationCode`, optional `displayName`, `locale`, `timezone`, `baseCurrency`, all required fields present, no unknown keys |
| Same payload, delivered through the client origin the browser uses | `202 accepted` (the contract is satisfiable exactly as the form builds it) |
| The invitation code stored for the preview account, validated with `invitationCodeSchema` | accepted — 35 characters, four groups of eight |
| 200 codes from `generateInvitationCode(20, 8)`, validated with the same schema | 200 accepted, 0 rejected — generator and contract agree |
| The published OpenAPI for `invitationCode` | `{type: string, minLength: 1, maxLength: 64}` — **no rule**, while the runtime required four Crockford groups of eight |
| The published OpenAPI for the service password policy | absent; the contract published `1–200` while the service enforces `12–128` and a common/similarity check |

The frontend form is therefore **not** the defect: it sends exactly the fields the
contract declares, and a body built that way is accepted. The defect is that the
API could not tell anyone what it had rejected, and that two enforced rules were
missing from the document callers are pointed at.

## The change

### 1. The response names the field and the rule

`packages/contracts/src/common.ts` — `errorResponseSchema.error` gains an optional
`fields` array of `{path, rule}` (`errorFieldSchema`), so every route that already
declares `errorResponseSchema` publishes it without a per-route edit. It is
optional and absent unless there is something to report, so no existing response
changes shape.

`apps/api/src/app.ts` — the validation branch now summarises the validator's
entries, logs that summary at `warn` against `correlationId: request.id`, and
includes it in the envelope. The ID the caller is shown is the ID in the log, so
the lookup that was impossible is now one `grep`.

### 2. The summary is value-free by construction

`apps/api/src/validation-detail.ts` (new) reads **only** `instancePath` and the
validator's issue `code`. It never copies the library `message` and never reads
`params`, because a validator issue can carry the submitted value and a message
can embed it — and a rejected body is exactly where passwords, invitation codes,
and one-time codes travel. The single exception is `unrecognized_keys`, where the
offending key names *are* the diagnosis; those pass a strict identifier filter
(`^[A-Za-z_][A-Za-z0-9_]{0,63}$`), are capped at 8 per entry, and the whole list
is capped at 20, so no free-form payload content and no amplification can reach
the response or the log.

### 3. The enforced rules are published

`packages/contracts/src/auth.ts`:

- `invitationCodeSchema` carries a `.describe(...)` stating the rule its `.refine`
  enforces. A `.refine` cannot become a JSON-schema `pattern`, which is why the
  rule was missing; a description survives transformation, so the requirement is
  now published next to the field. Acceptance behaviour is unchanged.
- `registerBodySchema.password` describes the transport bound **and** the service
  policy behind it (`400 AUTH_PASSWORD_POLICY_FAILED`). The note is attached to
  the register body only, because other endpoints reuse `passwordSchema` without
  being subject to the registration policy.

### 4. The client shows what the API reported

`apps/web/src/api.ts` parses `error.fields` defensively into `ApiFailure.fields`
(entries without a string `path` and `rule` are dropped, list capped at 20; a
missing or malformed list degrades to `[]` rather than to a guess).
`apps/web/src/dom.ts` renders the list under the message, next to the correlation
ID it already showed. The register form now states the invitation-code rule and
the enforced password policy in the field hints, so the round trip is usually
avoided entirely.

## Open findings (recorded, not hidden)

- **The reported attempt stays undiagnosed.** Its rejected field cannot be
  recovered, because nothing retained it. This addendum makes the *next* one
  identifiable; it does not retroactively explain this one.
- The invitation code is still hand-copied from an operator file into a form. The
  hint now states the format, but a mistyped code is still only detected on
  submit.
- `passwordSchema` remains `1–200` at the transport layer while the service
  enforces `12–128`. The boundary is now *documented* and *visible in the form*,
  but the two numbers are still different numbers; unifying them changes which
  error code a short password produces and was deliberately left out of this
  change set.
- The register endpoint is reachable only with an invitation code minted by an
  operator command; there is still no HTTP route that lists or re-issues codes by
  design (SEC-AUTH-14).

## Separate change carried in the same commit

Re-running the unit gate with `.env` sourced surfaced a test that was not
hermetic: `apps/web/test/dev-server.test.ts` passed the whole ambient environment
to the dev server it spawns, so the case that asserts "no outbox directory is
configured" inherited `EMAIL_OUTBOX_DIR` from the developer's shell and asserted
`404` against a `200`. It is fixed in the test (the helper no longer inherits that
one variable), it changes no product code, and it is recorded in
`docs/evidence/2026-10-12-LOCAL-APPLICATION-RUN.md` §4.3 with the reproduction
counts; without it the mandatory unit gate is red for anyone who follows the
documented run steps.
